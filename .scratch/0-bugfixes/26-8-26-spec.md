## 1. Notes app: dead tutorial checklist never hands off

**Problem:** Phone → Notes renders two stacked lists: `Todo.get_items()` (the M0 tutorial flag-chain) and `Todo.get_collective_items()` (the Collective arc's live objectives). The tutorial chain's last possible entry — "Archie's time vein is yours. Cultivate it. Harvest. Make pearls. Archie sells them." (`archiePartnerSeen` flag) — has no further flag to progress it. Once unlocked it sits permanently unchecked forever, stacked above the live Collective section, with nothing distinguishing "dead/finished" from "this is what you should do now."

**Where:** `systems/todo.gd` (`get_items()` lines 12-40, `get_collective_items()` lines 51-63 — note the latter already does this correctly: empties once `colA1Complete` is true, section disappears wholesale rather than item-by-item). `scenes/screens/phone.gd:320-340` (`_build_notes()`, stacks both cards).

**Decision:** Migrate the tutorial checklist onto the same Objectives system Collective already uses (`GameData.OBJECTIVES`, `systems/objectives.gd`, `state.objectives`), so Notes becomes a general objective tracker: one section per active questline, each backed by real objective state (title/detail/done), not an open-ended hardcoded flag chain. This is the general shape going forward — the tutorial is just the first migration; any future questline's Notes entries should use the same system rather than inventing another bespoke chain.

**Ticket guidance:** Author `data/objectives.json` entries for each existing tutorial checkpoint (`metArchie`, `buyerEventSeen`, `metJames`, `craftingUnlocked`, `archieCraftChatSeen`, `homeRaidEventSeen`, `archiePartnerSeen` — the exact flags `Todo.get_items()` currently reads), wire them into `state.objectives` activation/completion the same way Collective's are driven (check `systems/objectives.gd` and `systems/collective.gd` for the activation pattern used there), then delete `Todo.get_items()`'s flag-chain body and `phone.gd`'s dual-card rendering in favour of one unified "one section per active questline" loop over `GameData.OBJECTIVES`, grouped by whatever field distinguishes tutorial-origin objectives from Collective-origin ones (may need a new `questline` field in `objectives.json` if nothing already distinguishes them). Existing tutorial-progression tests (`tests/test_todo.gd`) will need rewriting against the new model, not just patching.

## 3 & 6. Map: vein doesn't visually connect / taps stop working — same root cause

**Problem (3):** Seeding a vein sometimes doesn't show its line connecting to the faction/player's tube line until the player leaves the Map tab and comes back.
**Problem (6):** After interacting with the Map tab for a while, tapping a district/vein sometimes does nothing, until leaving and returning to the tab.

**Root cause (confirmed in code, not just hypothesis):** `systems/map_events.gd`'s `playing` flag (`state.mapEvents.playing`) is a drain-guard for the map's animation queue. Its own comment (lines 248-258) documents the exact failure mode: if a queued event's animation is interrupted (e.g. a district-deck event firing mid-tween, navigating away) without going through `MapCanvas._exit_tree()`'s cleanup call to `MapEvents.abandon_playback()`, `playing` sticks `true` forever. Two consequences, both reported:
- While `playing` is stuck true, a vein queued via `queue_join_line()` stays hidden from the ordinary static line draw (`MapLayout`/`MapRouting` deliberately excludes any vein with a pending `join_line` event from the static picture — see `map_events.gd`'s `pending_join_line_vein_ids()`) — so it never visually connects until something drains or resets the queue. **This is item 3.**
- `MapCanvas._handle_tap()` (`scenes/components/map_canvas.gd:1547-1554`) checks `MapEvents.is_playing()` first and routes into `_skip_current()` instead of normal tap handling whenever it's true — with nothing actually queued to skip, this makes every tap a silent no-op. **This is item 6.**

Leaving the Map tab always fixes both, because `MapCanvas._exit_tree()` (line 355-360) unconditionally calls `MapEvents.abandon_playback()` on teardown, which force-clears `playing`. Returning gives a fresh, working canvas — until the same interruption happens again.

**Where:** `systems/map_events.gd` (`is_playing()` line 179, `begin_playback()` line 227, `advance()` line 238, `abandon_playback()` line 272 + its own comment explaining the exact bug). `scenes/components/map_canvas.gd` (`_exit_tree()` line 355, `_handle_tap()` line 1547, `_maybe_start_playback()`).

**Decision:** No design decision needed — this is a bug fix. No new UX behavior to define; the queue/animation system already has the right intended behavior, it's just leaking the stuck-flag state through an incomplete interruption path.

**Ticket guidance:** Find every code path that can interrupt/abandon a queued map event's playback *without* the Map screen (and therefore `MapCanvas`) actually being torn down — i.e., every place other than leaving the "map" screen that can stop a `_play_queue()` coroutine mid-flight. `abandon_playback()` already exists and does the right thing (pops the in-flight event, clears `playing`) — the fix is calling it from every interruption path, not just `_exit_tree()`. Prime suspect per the existing comment: a district-deck event firing mid-animation. Add a regression test that starts a queued animation, interrupts it via whatever path is found (not just tab-teardown), and confirms `is_playing()` recovers to false and a subsequent tap works normally — the existing test suite apparently doesn't cover the specific interruption path causing this, since it's shipped.

1. Archie/James — bespoke one-off SMS screens (`sms_archie.gd`/`sms_archie_2.gd`), launched from action-cards on the standalone `contacts` screen.
2. Des/Nadia/Hakim — exist *only* inside the generic Phone → Messages app's chat-thread UI (`systems/messages.gd`, `scenes/screens/phone.gd` `_build_messages`/`_build_conversation*`), with their story/trade actions bolted onto the bottom of the thread. They have no card on the Contacts screen at all.
3. The Contacts screen itself (`scenes/screens/contacts.gd`, added as its own reachable phone tile only recently by ticket 78) only ever built Archie's and James's cards (`ContactCards.build_archie_card()`/`build_james_card()`) — never extended to the other three.

Two top-level phone tiles exist for essentially the same concept ("Messages" and "Contacts"), pointing at inconsistent UIs.

**Where:** `scenes/screens/contacts.gd`, `scenes/components/contact_cards.gd` (`build_archie_card`, `build_james_card`, plus the Des/Nadia/Hakim action-builders `build_des_report_action` etc. currently only called from `phone.gd`), `scenes/screens/phone.gd:200-340` (Messages app), `scenes/screens/sms_archie.gd`/`sms_archie_2.gd`, `systems/messages.gd`, `systems/phone_apps.gd` (app registry, both `"messages"` and `"contacts"` tiles).

**Decision (revised from initial grill-me pass):** Contacts becomes the one hub. Kill the separate "Messages" phone tile. **Every contact card (Archie, James, Des, Nadia, Hakim) gets its own "Messages" button** that opens that contact's conversation thread (the existing generic thread UI from `phone.gd`'s Messages app, reused rather than rebuilt). For Archie and James, that thread must contain their **existing SMS content** (currently in the bespoke `sms_archie.gd`/`sms_archie_2.gd` screens) — folded into the generic thread rather than kept as separate bespoke screens. For Des, Nadia, and Hakim, the thread carries what's already in `state.messages` for them today, now surfaced via a "Messages" button on their own Contacts card instead of a top-level Messages app entry.

**Ticket guidance:** This is a genuine merge of two independent, currently-separate systems (the bespoke SMS screens' content/flow vs. the generic `Messages`/thread system) — expect it to touch `systems/events.gd` wherever `sms_archie`/`sms_archie_2` events get triggered (`archie_motion`/`james_motion` per existing `contacts.gd` comments) since their content needs to land in `state.messages` under the generic schema instead of a bespoke screen's own local state. Steps: (a) give Des/Nadia/Hakim proper Contacts-screen cards mirroring Archie/James's pattern (recruit row, standing/story actions per `ContactCards`'s existing per-contact action builders), each with a "Messages" button opening their existing generic thread; (b) port Archie's/James's SMS content into the generic `state.messages`/thread pipeline, add a "Messages" button to their existing cards, and retire `sms_archie.gd`/`sms_archie_2.gd`; (c) remove the `"messages"` entry from `PhoneApps.apps()` (`systems/phone_apps.gd`) and delete `phone.gd`'s conversation-list view (the per-contact thread view itself is kept, just reached from Contacts instead of a top-level list); (d) update `Messages.LEGACY_CONTACT_IDS` (or remove it, since Archie/James stop being the exception) and every test referencing the old split (`tests/test_phone_messages.gd`, `tests/test_contacts.gd`, `tests/test_contact_cards.gd`, `tests/test_phone_apps.gd`). ## 5. Bag drawer: completed device doesn't appear to equip

**Problem:** Player builds a device to completion at HQ; it never appears anywhere in the Bag drawer (🎒) to equip. Confirmed by the human as a genuine bug (device isn't listed at all), not a discoverability issue — they know to open the Bag.

**Explicit decision:** Equip stays in the Bag/inventory only (rejected: adding an equip affordance elsewhere, e.g. HQ). Find and fix whatever is actually breaking this — or, if investigation finds the feature is genuinely missing some piece, add it. Do not add a second equip surface.

**Where:** `scenes/components/bag_drawer.gd` — `_build_device_management()` (lines 206-256) and its gate `_is_management_mode()` (lines 147-156). `systems/devices.gd` — `_complete_device()` (appends to `player.devicesCompleted`), `equip_device()`. `systems/combat.gd` — `exit_combat()` (line 824, resets `state.combat` including `active: false`) and wherever `state.combat.active` is initially set true (line 258, combat-start dict literal).

**Investigation so far (ruled out / open leads for the ticket):**
- `_build_device_management()`'s rendering logic itself is correct and covered by passing tests (`tests/test_bag_drawer.gd` — `equip_and_unequip_device_from_the_drawer_matches_devices_system` and others) against hand-built state. Not the bug.
- `_is_management_mode()`'s `itemHooks` gate is currently unreachable in live data — `grep -rl itemHooks data/events/*.json` returns nothing, no authored card has it yet — so that half of the gate can't be what's hiding the button today. Ruled out.
- **Live open hypothesis:** `_is_management_mode()`'s *other* gate, `GameState.state["combat"]["active"]`, is a plain boolean with no assertion anywhere that it always returns to `false`. If it can get stuck `true` outside of an actual fight (mirroring the exact same class of bug found in item 3/6 above — an interruption that skips a system's own cleanup path), the Bag permanently falls back to its read-only view, which only ever shows the *currently equipped* device (`_build_equipped_device_label`) — an unequipped-but-completed device would never appear anywhere in that view, matching "isn't listed at all" exactly. `NavBar` excludes itself from the combat screen (R§2.2, `scenes/components/nav_bar.gd:9`) so the dock can't be used to escape combat without calling `exit_combat()` — but that doesn't rule out some *other* interruption path (an event firing during combat, a forced navigation, an ally/flee edge case) leaving `combat.active` stuck true the same way `map_events.gd`'s `playing` flag was found to leak. This needs the same treatment item 3/6 got: find the actual interruption path, don't just patch the symptom.
- Also worth checking directly, since it wasn't fully verified: whether `_complete_device()` (`systems/devices.gd`) is actually being reached and its `player.devicesCompleted.append(completed)` is actually landing in this specific repro — i.e. don't assume the stuck-gate theory without also confirming the device really is in `state.player.devicesCompleted` after the notification fires.

**Ticket guidance:** Reproduce end-to-end (start a device, drive `attempt_device_build()` to completion, then check both `state.player.devicesCompleted` directly and the Bag drawer's rendered output) rather than only unit-testing the render function against hand-built state — the existing test suite's gap is exactly that it never exercises the real completion→equip path together. If the `combat.active`-stuck theory confirms, find and close the interruption path (don't just add a safety reset — that treats the symptom, not the leak). Add a regression test covering whichever path is found.

## 7. Map: camera position/zoom no longer persists

**Problem:** Reopening the Map tab used to return to the same pan/zoom position; now it resets to default every single time, no exceptions.

**Context:** Not a missing feature — a regression of one. Tickets 53 and 67 (both `_COMPLETED`, `.scratch/0-bugfixes/issues/53-map-auto-focus-and-zoom-persistence_COMPLETED.md` and `67-map-camera-remembers-last-position_COMPLETED.md`) already built exactly this, including persisting across app restart. `systems/map_view.gd` (`MapView.save_view()`/`zoom()`/`scroll()`) and the persistence call sites in `scenes/components/map_canvas.gd` (`_exit_tree()` line 355-360 saves, `_apply_initial_view()` line 402-417 restores) all read as structurally correct against the ticket's own spec.

**Confirmed repro pattern:** fails every single time, no pattern — i.e. deterministic, not intermittent.

**Likely root cause (mechanical, not a design question):** `_apply_initial_view()` calls `_set_zoom(view["zoom"])` — which resizes the canvas via `_apply_zoom()` (`custom_minimum_size`/`size` change) — and then, in the same call, immediately sets the wrapping `ScrollContainer`'s scroll position via `_apply_scroll()`. Godot's `ScrollContainer` recomputes its valid scroll range from its child's size on layout, which can be deferred a frame; setting scroll before that recompute lands would get silently clamped back toward 0 against the container's still-stale (pre-resize) range. A deterministic "always resets" failure is exactly what that timing race would produce.

**Decision:** No design decision needed — this is a bug fix, not a UX choice. Behavior to restore is exactly what tickets 53/67 already specified.

**Ticket guidance:** Confirm the scroll-clamp-timing theory (check by deferring the `_apply_scroll()` call a frame — e.g. `call_deferred` or `await get_tree().process_frame` — after the resize, and see if persistence starts working) before assuming it's the whole story; if it doesn't fully explain the deterministic failure, keep digging rather than shipping a partial fix. Re-run/extend whatever manual or automated check tickets 53/67 originally used to confirm the regression is fully closed, not just improved.

## 8. Map: faction lines still cross other factions' veins

**Existing open ticket — amend, don't duplicate:** `.scratch/0-bugfixes/issues/74-map-faction-line-spacing-and-overlap-guarantee.md` already covers "a line must never visually cross a vein it doesn't own" and already correctly diagnoses the current best-effort routing's gap (falls back to a crossing path when both elbow orientations fail to clear an obstacle). It does **not** currently include the strategy confirmed in this grill-me session below — amend it to add that scope rather than opening a new ticket.

**Decision (new, from this session):** The human wants a hard guarantee, no visible gaps/breaks in the line. They are explicitly open to a vein's own map position shifting slightly to make that guarantee achievable — **small nudges from its original spot only**, not a full relayout. This goes beyond ticket 74's "add a further routing fallback" framing (which was pure path-routing, no repositioning) and beyond the "stub-only" scope — it turns this into a joint layout+routing problem.

**Tension to flag explicitly in the amended ticket:** `systems/map_layout.gd`'s `assign_positions()` and `systems/sites.gd`'s `next_slot_index()` currently guarantee a stop's position is **stable for its entire life** once assigned (explicit design intent, documented in both files' comments — this is also directly relevant to item 9 below, which touches the same mechanism). Allowing position to shift when a new line would otherwise have to cross it means this invariant now has an explicit, bounded exception: a stop may move, but only by a small, capped distance from its originally-assigned slot position — never a full re-layout, never unbounded drift. The amended ticket needs to define what "small" means concretely (a fixed max-offset in map px, proposed and flagged **needs visual sign-off** same as ticket 74's existing line-spacing value ask) and needs to decide whether a shift animates (and if so, whether it reuses `MapRouting.grow_segment()`'s animation-safe "guaranteed to end where the static draw already computes" pattern) or snaps.

**Where:** `systems/map_routing.gd` (`elbow_path`, `_elbow_crosses_stops`, `build_line`), `systems/map_layout.gd` (`assign_positions`, `group_by_faction`), `systems/sites.gd` (`next_slot_index`).

**Ticket guidance:** Amend ticket 74 in place (it's still `Status: ready-for-agent`, unclaimed) with this session's decision rather than filing a competing ticket. Keep ticket 74's existing line-to-line spacing requirement as-is — that part wasn't touched by this session.

## 9. Map: veins missing / unclaimed sites overlapping

**Problem:** A district's list view shows N veins belonging to a faction; the map visibly shows fewer. Unclaimed sites sometimes render stacked on top of each other, looking like one.

**Root cause (confirmed in code):** Every district's map-layout slot buffer is a consistent `siteCap + 2` (verified across all 9 districts against `data/districts.json`/`data/map_layout.json`) — sized correctly for the one case it was built for (a saturated site's bonus natural vein). But slot indices are handed out by `Sites.next_slot_index()` (`systems/sites.gd:49-53`), a per-district counter in `state.world.mapSlotCounters` that only ever increments — **explicitly documented as never reclaiming a removed stop's slot** ("trading the odd overflow ... for every still-live stop's position genuinely never moving underneath it," `systems/sites.gd:40-48`). Once a district's churn (sites/veins created and later removed — sold, collapsed, faction vein death, etc.) exceeds the fixed `+2` buffer, `MapLayout.assign_positions()` (`systems/map_layout.gd:65-82`) clamps every overflow item onto the same last slot, stacking multiple stops invisibly on top of each other. This is likely to get *worse* soon, not better — ticket 73 (just merged) deliberately increased faction vein claim/death churn rates.

**Decision:** Root-cause fix, not a band-aid: recycle a slot index back into its district's available pool when the site/vein occupying it is removed, so the counter never exhausts regardless of session length (rejected: just bumping the buffer size — delays but doesn't eliminate the problem).

**Where:** `systems/sites.gd:39-53` (`next_slot_index`), `systems/map_layout.gd:56-82` (`assign_positions`, `assign_slots`). Note this touches the same "position stability" mechanism as item 8's amendment to ticket 74 — coordinate the two if worked close together, since both are changing how/when a stop's slot position can change.

**Ticket guidance:** Add a per-district free-list (e.g. `state.world.mapSlotFreeList[district_id]: Array[int]`) that `next_slot_index()` pops from before incrementing its counter. The harder part is finding and instrumenting every removal path — every place a site or vein stops existing in a district (vein sold to a faction and the site's own slot changes hands, `Cultivating.collapse_vein()`, faction vein death via prune-back/collapse, any other site-removal path) needs to push its freed `slotIndex` onto that district's free list. Enumerate these call sites explicitly in the ticket (ticket 73's own progress notes, now in `73-faction-vein-churn-balance_COMPLETED.md`, are a good map of where faction vein death currently happens). Add a test that seeds enough churn in one district to exceed the old fixed buffer and confirms no two live stops ever end up clamped onto the same slot.
