# 44 — Archie as combat ally (vein defense)

**What to build:** Combat is currently strictly 1v1 — `combat` state holds a single `"enemy"` dict, not an array (`systems/combat.gd:210,221,250,296,416,472,618,704`), and `contacts.gd` has no ally/companion concept at all. Add Archie as a real second combatant in vein-defense fights: once Archie is recruited, he's always available to join (no relation threshold — per the human, defending shared interests doesn't need much trust). Mechanically, Archie acts as a genuine second attacker each turn alongside the player (not a passive stat buff), and he carries his own small consumable stash that replenishes between fights (independent of the player's inventory). He has his own HP pool — if it hits 0 he's knocked out and removed from that fight (or unavailable for some cooldown period), giving the mechanic real stakes without permadeath.

This is the foundational ticket for the ally-combat system — build the combat-state shape (allies, not just a single enemy) and Archie's participation generally enough that a future recruit can plug into the same system later (per the human: "Archie-only for now, but other characters will be recruitable in the same way later"), but only wire up Archie in this pass.

**Blocked by:** None — can start immediately.

**Status:** completed

- [x] `combat.allies` added: an array of general-shaped ally dicts (`{contactId, name, hp, hpMax, attackMin, attackMax, stash, healAmount, koed}`), alongside the existing single-`enemy` shape. `Contacts.can_join_combat()`/`build_combat_ally()` are contact-id-generic — any future recruit whose `constants.json` entry defines a `combatHpMax` plugs in unmodified; `james` deliberately has none yet (`combatHpMax: 0`), so only Archie is ever offered in this pass.
- [x] `Combat.start_defend_vein()` auto-joins every contact `Contacts.can_join_combat()` allows (recruited + has a combat kit + not on KO cooldown — no relation threshold) as a second attacker. No offer/decline step, per the human's "defending shared interests doesn't need much trust."
- [x] Each player-attack turn, every non-KO'd ally acts once (`Combat._allies_act()`): attacks the enemy with their own attackMin/attackMax (can win the fight outright), or — below 40% of their own hpMax with a stash charge left — spends one charge to heal themselves instead, and the stash depletes accordingly. **Design call, not spec-specified:** the ticket didn't say what the stash is *for*; I built it as a self-heal-below-threshold charge (own `healAmount` constant) rather than tying it to the player's real consumable items, since a contact having its own item-crafting/inventory system was out of scope. Worth a look if that's not the intended flavour.
- [x] Archie has his own HP pool (`combatHpMax`/`combatHp`, 50). The enemy's one attack per turn now targets the player or a random non-KO'd ally (**also a design call**: the spec didn't say how the enemy picks a target — without this, nothing could ever put Archie's HP at risk). At 0 hp, `ally.koed = true` removes him from all further turn/target logic that fight (`combat.outcome` stays untouched — the fight continues for the player) and `Contacts.knock_out()` sets a 2-day cooldown (`koCooldownUntilDay`) before he's eligible to join again. `Contacts.replenish_after_combat()` tops every fought ally's hp/stash back to max when the fight ends (the chosen "replenish" trigger) — the cooldown itself is untouched by this.

- [x] New tests: `tests/test_combat.gd` (ally joins a defend fight / doesn't join when not recruited, ally attacks each turn, ally heals from stash and it depletes, enemy can target and KO an ally without ending the fight, exit_combat replenishes hp/stash but leaves the KO cooldown alone) and `tests/test_contacts.gd` (`can_join_combat` eligibility incl. no-relation-threshold and cooldown gating, `build_combat_ally`, `knock_out`, `replenish_after_combat`).
