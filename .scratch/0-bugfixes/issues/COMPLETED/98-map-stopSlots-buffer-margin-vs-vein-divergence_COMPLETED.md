# 98 — Map: stopSlots buffer margin can't cover multiple concurrently-diverged sibling veins

**What to build:** Ticket 94 fixed a rendering bug where a saturated site's natural-vein bonus (a second vein at the same site, its own stamped slotIndex, independent of the site's own slot — see docs/M1-LONDON.md's hasNaturalVein bonus) would silently vanish from the map once its sibling vein left the site on its own (sold via VeinTrade.sell_to_faction, raided away via Raiding.resolve_raid_outcome's claim branch, or collapsed via Cultivating.collapse_vein's player branch). That fix makes such a "diverged" bonus vein render correctly again — but it exposed a deeper capacity assumption that was never actually validated: `data/map_layout.json`'s per-district `stopSlots` buffer is sized `siteCap + 2` (GameData.gd's boot-time validator, ~line 738), and the `+2` margin was reasoned (52-map-vein-line-position-drift's own comments) as "covers the one extra stop a claimed site's natural-vein bonus can add" — i.e. it assumes **at most one** site in a district ever has its two veins in a diverged state (one gone, one still live) at the same time.

That assumption doesn't hold once a site's two veins can leave the site independently rather than always together. A diverged bonus vein keeps its own slot pinned live for as long as it survives — which could be a long time, since nothing forces it to resolve quickly. If a second (or third...) hasNaturalVein site in the same district independently diverges while the first one is still pinning its extra slot, the district's live stop count can exceed `siteCap + 2`, and `MapLayout.assign_positions()`'s overflow clamp (`mini(item.slotIndex, slots.size() - 1)`) will clamp two distinct live stops onto the same final slot — a real visual overlap, not just a missing render. This is very likely the actual mechanism behind this bug thread's second reported symptom ("unclaimed sites sometimes render stacked on top of each other, looking like one") that ticket 94's rendering fix doesn't address, and it's plausibly more reachable now than when the buffer was first sized, since bugfixes-73 deliberately increased faction vein churn (more raids, more claims) — more churn means more chances for two separate sites to diverge in the same window.

Worst case is bounded (only currently-claimed sites can diverge, and only hasNaturalVein ones have a second vein to diverge — so at most `siteCap` such divergences could theoretically overlap in one district at once), but that worst case is `siteCap` extra slots, not the `+2` the buffer currently budgets.

Two different ways to close this, needing a human call before an agent should pick one (bugfixes-94's own investigation flagged this rather than guessing):

- **Balance change:** widen the per-district buffer margin (e.g. `siteCap * 2` as a provably-safe worst case, or something smaller if a tighter realistic ceiling on concurrent divergences can be justified) in `data/map_layout.json` and `GameData.gd`'s validator. Bigger buffers likely mean revisiting each district's `stopSlots` pixel layout in map_layout.json (more literal positions to hand-place), which is a content/design pass, not just a number bump.
- **Mechanics change:** make a site's two veins always move or die together (selling/raiding/collapsing one also resolves the other), closing off divergence at the source instead of accommodating it. Keeps `siteCap + 2` valid as originally reasoned, but changes player-facing behavior around the natural-vein bonus — arguably a bigger deal since it changes what selling/raiding a hasNaturalVein site's vein *means* to the player.

**Where:** `data/map_layout.json` (stopSlots per district), `autoload/GameData.gd` (~line 692-740, the `siteCap + 2` validation), `systems/map_layout.gd` (`assign_positions`'s clamp), or — if the mechanics route is chosen instead — `systems/cultivating.gd` (`collapse_vein`), `systems/vein_trade.gd` (`sell_to_faction`), `systems/raiding.gd` (`resolve_raid_outcome`).

**Blocked by:** A human decision on which remediation route (balance vs. mechanics) above, and (if balance) what margin/methodology to use — needs balance sign-off, same as every other numeric tuning call in this bug thread's history.
