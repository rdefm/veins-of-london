# Bug hunt — 2026-07-17

Ran the project for real (headless, via the bundled `Godot_v4.4-stable_win64_console.exe`)
and drove the actual test suite (`tests/test_runner.gd`, 178 cases across 26 files)
instead of just reading code. Findings below. One root cause is fixed and
verified; two are diagnosed but not yet fixed, pending a decision on
approach.

## How to reproduce / continue

```
./Godot_v4.4-stable_win64_console.exe --headless -s tests/test_runner.gd
```

(`scripts/run_tests.sh` assumes a `godot` binary on PATH or a `./godot`
symlink — neither exists on this Windows checkout; the Linux binary
`./godot` can't run here. Invoke the `.exe` directly instead, or fix the
script to look for it.)

## 1. FIXED — GameData never loaded before tests ran (51 failing tests)

**Symptom:** 51 of 178 tests failed with runtime errors like
`Invalid access to property or key 'economic' on a base object of type
'Dictionary'`, scattered across barometer, crafting, cultivating, devices,
home, economy, sell, and save/load tests.

**Root cause:** `tests/test_runner.gd` is a `SceneTree`-extending script
run via `godot --headless -s tests/test_runner.gd`. It does all its work
synchronously inside `_initialize()` and never lets a frame process. Autoload
`_ready()` callbacks (including `GameData._ready()`, which calls
`load_all()` to parse every `data/*.json` file) are queued as deferred
notifications that only fire once the engine actually iterates the main
loop — which never happens here, since `_initialize()` runs to completion
(or, in the broken version, the script just runs straight through) without
yielding a frame. So every `GameData.*` table (`BAROMETER_STATES`,
`RECIPES`, `ORE_TYPES`, `CONTACTS_DEFAULTS`, `HOME_TIERS`, ...) sat at its
empty default (`{}`) for the entire test run. Confirmed by instrumenting
`GameData._ready()` directly — it doesn't run until the very last few
lines of a full test-suite pass.

I initially tried `await process_frame` at the top of `_initialize()` to
force a frame to process — this genuinely fixed the GameData-empty problem
(failures dropped 51 → 2) but introduced a **new hang**: the test run got
partway through the suite and never returned. Root-caused that too (see §2
below) — it wasn't the await itself, it was that fixing GameData exposed a
real, separate perf bug in two integration tests that only run/matter once
real data is present. But since `await` adds a coroutine-suspension
dependency that's touchy under a custom SceneTree main loop, I reverted it
in favour of a more surgical fix.

**Fix applied** (`tests/test_runner.gd`, top of `_initialize()`):

```gdscript
var game_data: Node = root.get_node_or_null("GameData")
if game_data != null and not game_data.loaded:
    game_data.load_all()
    game_data.validate()
```

`GameData` (the Node) already exists as a child of `/root` at this point —
it's just its own deferred `_ready()` that hasn't run — so `get_node_or_null`
finds it and we can call `load_all()`/`validate()` on it directly,
synchronously, with no coroutine involved. Idempotent and harmless if
`_ready()` does eventually fire later (it just repopulates the same
dictionaries).

**Status:** Fixed and verified. Failure count went from 51 → 2 (see §3).
This is a test-infrastructure-only fix; `scenes/Main.gd`/normal game boot
via `Main.tscn` goes through the engine's regular frame-based
initialization and was never affected — only the synchronous `-s` test
runner was.

## 2. NOT FIXED — `test_events.gd` and `test_playthrough.gd` integration
   tests hang / are extremely slow once GameData is populated

**Symptom:** With GameData now actually loaded, `test_events.gd`'s
`full_tutorial_playthrough_lands_every_r311_change` case and the entire
`test_playthrough.gd` file no longer fail fast — they run for minutes
without completing. A run capped at 5 minutes was still climbing through
individual `Events.advance()` calls without erroring.

**What's confirmed:**
- It is **not** a crash and not a script error — no error output at all,
  just increasingly slow (or truly stalled) progress.
- Bisected via inline `print()` instrumentation (since removed) to
  `Events.advance()` calls partway through the `james_meeting` event's
  24-card sequence — cards kept advancing (card 15, 16, 17, 18...) but each
  one seemed to take longer, consistent with **O(n²)/quadratic growth**
  rather than a true infinite loop in a single call.
- The prime suspect is `Events.advance()` → `Snapshots.push()`: every
  single `advance()` call does a full `GameState.deep_copy(GameState.state)`
  and pushes it onto `state.event.snapshots` (for rewind support). Across a
  ~250-card full tutorial + 300-try `_find_seed_for` retry loops (each of
  which also does `GameState.deep_copy` per attempt) in
  `test_playthrough.gd`, the accumulated deep-copy volume could plausibly
  become the bottleneck — but this needs profiling, not assumption.
- Not yet ruled out: `Snapshots.gd`'s stack-size cap/eviction logic (does it
  actually cap growth, or grow unbounded per event?), or something
  specific to `james_meeting`'s card list length (it's the longest event,
  24 cards) versus `intro`/`buyer` (which passed quickly, ~12 cards each).

**What's NOT the cause** (ruled out by reading):
- No unbounded `while` loops in `systems/combat.gd`, `systems/events.gd`,
  `systems/time_system.gd`, `systems/contacts.gd`, `systems/rooms.gd` —
  all loops found are bounded by skill-level caps, ingredient counts, or
  fixed ranges.
- Not GDScript's `await`/coroutine mechanics — reproduced the same hang
  location with a version of `test_runner.gd` that has no `await`
  anywhere.

**Next steps:**
1. Profile a single `Events.advance()` call late in `james_meeting` vs.
   early — confirm the O(n²) hypothesis directly (e.g. temporarily log
   elapsed time per `advance()` call).
2. Check `autoload/Snapshots.gd`'s push/cap logic — R§ presumably specifies
   a max rewind depth; if the stack isn't actually capped, that's the bug
   and the fix is enforcing the cap on push.
3. Once fixed, re-enable and time the full suite — `scripts/soak.sh` (20x
   full-suite run) will be a good regression guard for this specifically,
   since it's a perf issue that a single fast pass might mask if the cap
   fix isn't quite right.

**Workaround for now:** none applied — both tests are untouched and will
still hang if the full suite is run to completion. Cap your `timeout` when
running `tests/test_runner.gd` (30–40s is enough to get through everything
before `test_events.gd`) until this is fixed.

## 3. NOT FIXED — 2 genuine `test_eventbus.gd` failures (GDScript closure
   semantics, not a game bug)

**Symptom:**
```
FAIL: screen_changed_carries_the_screen_name
      assert_eq: got , expected veins.
FAIL: day_ticked_carries_the_day_number
      assert_eq: got -1, expected 4.
```

**Root cause (confirmed via isolated repro):** both test cases do this
pattern:

```gdscript
var received := ""
var on_screen := func(screen: String): received = screen
EventBus.screen_changed.connect(on_screen)
EventBus.screen_changed.emit("veins")
assert_eq(received, "veins", ...)
```

GDScript lambdas **capture outer local variables by value, not by
reference** — assigning to `received` inside the lambda rebinds the
lambda's own private copy, never the outer `received` in `run_case`'s
scope. Verified directly:

```gdscript
var received := "start"
var fn := func(x: String): received = x
fn.call("changed")
print(received)  # prints "start", not "changed"
```

So `EventBus.screen_changed`/`day_ticked` themselves are almost certainly
fine (they're one-line `signal` declarations with plain `.emit()` calls
elsewhere in the codebase, working correctly everywhere else) — **the test
itself is written in a way GDScript doesn't support.**

**Fix direction (not applied yet — needs a decision):** the usual GDScript-native
fix is to capture a mutable container instead of a plain variable, e.g.:

```gdscript
var received := [""]
var on_screen := func(screen: String): received[0] = screen
EventBus.screen_changed.connect(on_screen)
EventBus.screen_changed.emit("veins")
assert_eq(received[0], "veins", ...)
```

(Arrays/Dictionaries are still captured by value as a *reference to the same
object*, so mutating elements in place works.) Left unfixed pending sign-off
since it changes an existing test file's assertions style — flagging
rather than silently changing test semantics.
